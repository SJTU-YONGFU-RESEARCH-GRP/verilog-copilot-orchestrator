### Overview

This repository is an **AI‑assisted Verilog/SystemVerilog RTL lab** that turns GitHub Issues into a structured hardware design workflow.  
It uses **issue templates**, **GitHub Actions**, and **AI agents** to generate and iterate on:

- **RTL modules** in `rtl/`
- **Testbenches** in `tb/`
- **Module documentation** in `docs/`
- **Traceability and results JSON** in `results/`

The core idea is to let you describe what you want in natural language and then drive a **repeatable, testable, reviewable** flow from **Specification → Implementation → Verification**, with strong emphasis on **simulation and JSON traceability**.

This project is **experimental** and intended as a lab / workflow template rather than production silicon sign‑off.

---

### Features

- **End‑to‑end AI pipeline**
  - Reads `docs/ARCHITECTURE.md` and `docs/PLAN.md` as **sources of truth**
  - Generates RTL, testbenches, and module docs
  - Writes JSON status to `results/phase-*/`
- **Issue‑driven workflow**
  - **AI Specification**: Architecture generation and refinement
  - **AI Implementation**: Module‑by‑module RTL/TB/docs generation
  - **AI Verification**: Extra tests, constraints, and refinements
- **Simulation‑first**
  - Validates modules using `iverilog` + `vvp` (SystemVerilog `-g2012`)
  - Requires successful simulation before marking tasks as done
- **Traceability & auditability**
  - Per‑module JSON files encode status, coverage, and log paths
- **Auto‑merge gate**
  - Label PRs as `ready-to-merge` to trigger automated merging

### Repository Layout

The workflow expects the following structure:

- **`rtl/`** – Synthesizable RTL modules  
  - `rtl/<module>.v`
- **`tb/`** – Unit testbenches  
  - `tb/<module>_tb.v`
- **`docs/`** – Documentation  
  - `docs/ARCHITECTURE.md` – authoritative architecture reference  
  - `docs/PLAN.md` – implementation phases and checklists  
  - `docs/<module>.md` – per‑module docs generated by the workflow
- **`results/`** – Validation artifacts and JSON summaries  
  - `results/phase-<phase_name>/<module>_result.json`  
  - Associated logs, e.g. `sim_log` files
- **`.github/ISSUE_TEMPLATE/`** – Issue templates that drive the workflow  
  - `1_specification.yml` – AI Specification  
  - `2_planning.yml` – AI Planning (structure reference)  
  - `3_implementation.yml` – AI Implementation  
  - `4_verification.yml` – AI Verification
- **`.github/instructions/` + `docs/*.md`** – Internal instructions for agents and users  
  - `.github/copilot-instructions.md`  
  - `docs/INSTRUCTION.md` – human‑readable workflow guide  
  - `docs/ARCHITECTURE.md`, `docs/PLAN.md` – primary context for AI agents

### Workflow Usage – High‑Level

The main interaction model is:

1. **Create a GitHub Issue** using one of the AI templates.
2. Let the **`ai-pipeline.yml`** workflow react to the issue.
3. Review the generated **code, docs, and JSON** in a pull request.
4. When satisfied, label the PR as **`ready-to-merge`** to auto‑merge.

The workflow **routes by parsing the issue body**, not by labels.  
Labels (like `AI-task`, `rtl`, `tb`, `doc`, `verification`) are for human filtering only and must exist in the repo.

For a full narrative walkthrough, see `docs/INSTRUCTION.md`.

### Before You Start – Fork and Setup

- **Fork this repository** on GitHub if you are experimenting:
  - Run issues and PRs in your **fork**.
  - Keep this template repo clean.
- **Clone your fork** locally:

```bash
git clone https://github.com/SJTU-YONGFU-RESEARCH-GRP/verilog-copilot-workflow.git
cd verilog-copilot-workflow
```

- Ensure you have:
  - **`iverilog`** and **`vvp`** installed (for local simulation).
  - GitHub Actions enabled for the repo.
  - The **Issues** feature enabled on your fork (Settings → General → Features → check **Issues**) so that the AI issue templates and workflow can be used.

> For multiple experiments, use different **branches** in a single fork.  
> The pipeline itself creates `ai/rtl-*`, `ai/tb-*`, and `ai/doc-*` branches during runs.

### Step 1 – AI Specification (Architecture)

**Goal:** Turn a rough design idea into a structured architecture document.

1. On GitHub, click **“New issue”**.
2. Choose the **“AI Specification”** template (`1_specification.yml`).
3. Make sure the issue is **assigned to `github-copilot`** (the templates do this by default; if you changed assignees, ensure the Copilot/bot account is selected so the workflow runs).
4. Fill in:
   - **Idea or description (optional)** – high‑level RTL idea.
   - **Standards / reference documents (recommended)** – e.g. JEDEC/AXI/PCIe; include names, versions, and public links when possible.
5. Submit the issue.

The AI pipeline will:

- Read existing architecture (`docs/ARCHITECTURE.md` if present).
- Generate or update **`docs/ARCHITECTURE.md`** with:
  - Project overview
  - Functional blocks / modules
  - Interfaces and I/O
  - Timing, protocols, constraints
  - Optional block diagrams or FSMs

You can iterate by editing `docs/ARCHITECTURE.md` directly and/or re‑running Specification issues as requirements evolve.

---

### Step 2 – AI Implementation (RTL, Testbench, Docs)

**Goal:** For a given module, generate RTL, testbench, documentation, and results.

1. On GitHub, click **“New issue”**.
2. Choose the **“AI Implementation”** template (`3_implementation.yml`). 
3. Make sure the issue is **assigned to `github-copilot`** (or the bot/user that runs this workflow) so that PR generation is triggered.
4. Fill in:
   - **Module name (required)** – must match the module name in `docs/ARCHITECTURE.md` / `docs/PLAN.md`, e.g. `ddr4_ctrl_top`.
   - **Description (optional)** – additional context; can be left blank.
5. Submit the issue.

The **`ai-pipeline.yml`** workflow will:

- Detect this is an **Implementation** issue.
- Build a context bundle from:
  - `docs/ARCHITECTURE.md` (or root `ARCHITECTURE.md`)
  - `docs/PLAN.md` (if present)
  - Optional docs like `INTERFACE_SPEC.md`, `TESTPLAN.md` (root or `docs/`)
- Call AI agents to generate:
  - `rtl/<module_name>.v`
  - `tb/<module_name>_tb.v`
  - `docs/<module_name>.md`
  - `results/phase-<phase_name>/<module_name>_result.json` + logs
- Open PRs from `ai/rtl-*`, `ai/tb-*`, `ai/doc-*` branches into your default branch.

You then review and, when ready, label the PR as **`ready-to-merge`**.

---

### Step 3 – AI Verification & Auto‑Merge

**Goal:** Tighten tests/constraints, refine RTL/docs, and use **auto‑merge** when ready.

1. For an **Implementation PR**:
   - Review the RTL, TB, docs, and JSON in `results/`.
   - Optionally run additional local simulations (see next section).
2. When the PR looks good:
   - Add the label **`ready-to-merge`** to the pull request.
3. The `ai-pipeline.yml` workflow listens for `pull_request: labeled` events:
   - When it sees `ready-to-merge`, it **automatically merges** the PR into the default branch.
4. If you need **more tests or refinements**:
   - Open a **“AI Verification”** issue (`4_verification.yml`).
   - Optionally specify:
     - **Module name**
     - **What do you want to improve?** (tests, constraints, RTL/docs)
   - Use Verification issues to drive coverage, corner cases, or refactoring.

You can repeat Implementation and Verification issues as much as needed.

### Local Simulation Workflow

The repo enforces a **hard validation gate** using `iverilog` and `vvp`.  
For each module `<module>`:

- **Compile:**

```bash
iverilog -g2012 -o build/<module>.out tb/<module>_tb.v rtl/<module>.v
```

- **Run:**

```bash
vvp build/<module>.out
```

- **Expectations:**
  - Tests must pass deterministically.
  - Testbenches should include clock/reset and typically produce a VCD for debugging.
  - You should only mark `simulation_passed: true` in JSON when `vvp` exits successfully.

### Results & Traceability JSON

For each module and phase, the workflow maintains a JSON status file:

- **Location:**  
  - `results/phase-<phase_name>/<module>_result.json`

- **Required fields (conceptual):**
  - `module`
  - `rtl_done`, `tb_done`, `doc_done`
  - `simulation_passed` (true only if `vvp` succeeds)
  - `coverage_completed`, `coverage_percentage`
  - `plan_item_completed` (true only if RTL + TB + docs exist and simulation passes)
  - `error_summary` (empty if all good; otherwise a brief reason)
  - `sim_log` (path to simulation log under the same `results/phase-.../` directory)

These files provide machine‑readable traceability and help enforce that completed plan items are genuinely validated.

### Implementation Plan & Phases

`docs/PLAN.md` describes how work is broken into phases and checklists. Agents are expected to:

- **Use `docs/PLAN.md`** to determine which modules and tasks to implement.
- Prefer a **“phase‑first, gated completion”** approach:
  - Pick the first phase with unchecked items.
  - Implement **all modules** in that phase (RTL, TB, docs, results) before moving on.
- Never claim completion unless:
  - Simulation has passed.
  - JSON in `results/` reflects accurate status.

You are free to edit `docs/PLAN.md` as your design grows; the workflow will simply consume the updated plan.

### Contributing

- **Issues & templates**
  - Use the AI templates under `.github/ISSUE_TEMPLATE/`.
  - Ensure labels like `AI-task`, `rtl`, `tb`, `doc`, `verification` exist under **Issues → Labels**.
  - Default assignee is `github-copilot`. To change it, edit the `assignees` field in each template.
- **Pull requests**
  - Review generated changes carefully, especially for non‑trivial designs.
  - Add `ready-to-merge` to PRs once you are confident in correctness and coverage.
- **Extending the workflow**
  - Use `.github/instructions/*.md` and `.github/agents/prompt-templates/` as guides when adjusting prompts or behaviors.
  - You can add custom phases, additional result fields, or extra validation jobs as needed.
